오늘의 뉴스는 서로 달라 보이지만 한 문장으로 묶인다. **도구의 기능 목록이 아니라, 실패했을 때 누가 어떤 근거로 되돌릴 수 있는가가 기술 선택의 중심이 됐다.** AI가 만든 패치, 새 언어 릴리스, 이미지 포맷, 인터넷 라우팅 보안까지 모두 배포·검증·호환성의 문제로 귀결된다. [AI 코드 리뷰 거버넌스](/posts/2026-03-06-ai-code-review-governance-trend/)에서 다룬 “생성보다 검증” 원칙을 오늘의 네 이슈에 적용해 보자.

## 1. AI 보조 커널 기여: 자동화의 경계는 책임 추적성이다

**사실 요약.** Lobsters에서 Linus Torvalds의 AI 보조 커널 기여 관련 메일이 논의됐다. 핵심은 AI 사용 여부를 선언하는 형식 문제가 아니라, 제출자가 변경의 의미와 실패 모드를 이해하고 검증 가능한가에 있다. 대형 오픈소스 프로젝트의 리뷰는 여전히 저자 책임과 재현성을 요구한다.

**왜 중요한가.** 사내 저장소도 같은 압력을 받는다. 에이전트가 만든 작은 변경 여러 개는 사람 한 명이 만든 큰 변경보다 리뷰 비용을 낮추지 않을 수 있다. 원인 추적이 어려운 회귀, 라이선스·비밀정보 혼입, 테스트가 통과해도 깨지는 운영 가정이 누적되면 배포 속도는 오히려 느려진다.

**시니어 코멘트.** AI 작성 코드는 “작성자”가 아니라 “제안자”로 취급하자. PR에는 문제 정의, 변경 불변식, 실행한 테스트, 되돌림 기준을 자동으로 채우게 하고 소유자가 승인해야 병합되도록 만든다. 권한·결제·마이그레이션 경로는 자동 병합 대상에서 제외한다. 이는 [에이전트 권한과 운영 경계](/posts/2026-09-28-managed-agent-harness-ownership-boundary-trend/)를 코드 리뷰에 적용하는 가장 작은 단위다.

## 2. Rust 1.99.1: 버전 업은 언어 뉴스가 아니라 공급망 변경 관리다

**사실 요약.** Rust 프로젝트는 10월 15일 Rust 1.99.1 릴리스를 공지했다. 마이너 패치 릴리스라도 컴파일러·표준 라이브러리·도구 체인의 조합이 바뀌며, 워크스페이스 lockfile과 CI 이미지가 실제 영향 범위를 결정한다.

**왜 중요한가.** “패치 버전이니 안전하다”는 판단은 네이티브 의존성, 매크로, 빌드 스크립트가 있는 서비스에서 성립하지 않는다. 개발자 로컬의 성공과 릴리스 이미지의 성공이 다르면 장애는 코드가 아니라 빌드 재현성에서 시작한다. 언어 업그레이드는 보안 패치와 생산성 개선을 가져오지만 캐시 무효화와 바이너리 호환성 비용도 만든다.

**시니어 코멘트.** 기본 브랜치의 도구 체인은 고정하고 업그레이드는 전용 PR에서 fmt→clippy→test→release build→대표 부하 시나리오 순으로 승격하자. CI에는 현재 안정판과 후보판을 병렬로 돌려 경고를 미리 수집하되, 후보판 실패를 곧바로 제품 배포 실패로 만들지는 말아야 한다. 의존성·도구 버전·빌드 이미지를 한 변경 묶음으로 리뷰하는 것이 핵심이다.

## 3. JPEG XL 대 AVIF: 이미지 포맷 선택은 압축률 경쟁이 아니라 브라우저 계약이다

**사실 요약.** 웹 이미지 용도에서 JPEG XL과 AVIF를 비교한 글이 화제가 됐다. 두 포맷 모두 현대적 압축과 고급 색상 표현을 제공하지만, 실제 채택성은 파일 크기 하나가 아니라 브라우저 지원, 디코딩 비용, 기존 파이프라인과의 연결성에 좌우된다.

**왜 중요한가.** 이미지 최적화는 CDN 비용과 LCP를 함께 움직인다. 지원이 고르지 않은 포맷을 원본처럼 쓰면 폴백, 캐시 키, 관측 지표가 복잡해진다. 평균 바이트 절감만 보고 전환하면 저사양 기기에서 디코딩 지연이 커지거나 특정 브라우저에서 품질·호환성 사고가 날 수 있다.

**시니어 코멘트.** 전역 교체보다 트래픽이 큰 세 페이지에서 폴백을 포함한 실험으로 시작하자. 전송 바이트뿐 아니라 LCP p75, 이미지 오류율, 디코드 긴 작업, CDN hit ratio를 함께 본다. 원본 보관과 재인코딩 가능성을 유지하고 캐시 무효화 비용이 절감액을 넘으면 중단한다. API 경계도 “지원”보다 소비자 계약이 먼저라는 점은 [gRPC·REST·GraphQL 선택 기준](/posts/2025-03-15-1-grpc-vs-rest-vs-graphql/)과 닮았다.

## 4. RPKI가 보호하는 경로 70%: 네트워크 보안은 도입률보다 거부 모드가 중요하다

**사실 요약.** IPinfo는 RPKI가 인터넷 라우트의 70%를 보호하는 수준에 도달했다고 분석했다. RPKI는 어느 AS가 어떤 IP 프리픽스를 광고할 수 있는지 검증하는 기반이며, 경로 하이재킹과 잘못된 라우팅 광고의 피해를 줄이는 데 쓰인다.

**왜 중요한가.** 애플리케이션 팀은 BGP를 직접 만지지 않아도 외부 API, CDN, SaaS 의존성이 라우팅 사고의 영향을 받는다. 보호율이 높아지는 것은 좋은 신호지만 검증을 invalid에서 실제 차단하는 비율과 공급자별 정책이 다르면 체감 위험은 달라진다. “보호됨”이라는 배지가 가용성 검증을 대신할 수 없다.

**시니어 코멘트.** 자사 프리픽스의 ROA 정확성부터 확인하고 invalid 경로를 관측-only로 본 뒤 차단으로 올려라. 제품팀은 주요 외부 의존성의 다중 리전·다중 공급자 경로와 DNS 전환 시간을 게임데이로 검증해야 한다. 인증서, DNS, 라우팅처럼 평소 보이지 않는 기반은 장애 시에만 드러난다. [64일 인증서와 운영 경계](/posts/2026-10-09-dev-news-senior-insights/)의 교훈도 동일하다.

## 5. Self-Evolving Agent Harness: 스스로 고치는 하네스는 스스로 넓히는 권한이 되어서는 안 된다

**사실 요약.** GeekNews에는 프롬프트·기억·도구 구성을 스스로 개선하는 에이전트 하네스가 소개됐다. 모델 자체를 바꾸지 않고 실행 컨텍스트를 반복 개선해 성능을 높이려는 접근이다. 모델 교체보다 빠르게 팀별 작업 절차를 최적화할 수 있다는 기대를 만든다.

**왜 중요한가.** 하네스가 바뀌면 모델 버전이 같아도 결과가 달라진다. 프롬프트 변경, 도구 선택, 메모리 회수 정책은 사실상 프로덕션 코드다. 성능 지표만 최적화하면 비용이 폭증하거나 잘못된 기억이 강화되거나 안전 제약이 조금씩 약화될 위험이 있다.

**시니어 코멘트.** 하네스 변경은 버전 관리하고 기준 작업 묶음과 안전성 회귀 세트를 통과해야 승격하자. 개선안은 sandbox에서 먼저 실행하며 파일 쓰기·배포·외부 전송 권한은 하네스가 직접 확대하지 못하게 분리한다. 성공률 외에 작업당 비용, 사람 개입률, 정책 위반률, 되돌림 시간을 대시보드에 올려야 한다. 에이전트 도입의 병목이 연결성이 아니라 신뢰라는 점은 [AI 에이전트 운영 경계](/posts/2026-08-21-dev-news-senior-insights/)에서도 확인할 수 있다.

## 오늘의 실행 체크리스트

1. AI가 만든 PR에 변경 불변식·테스트·되돌림 기준을 필수 템플릿으로 추가한다.
2. 다음 Rust 도구 체인 업그레이드를 후보판 CI와 릴리스 빌드로 분리해 검증한다.
3. 상위 트래픽 페이지 한 곳에서 AVIF/JPEG XL 폴백 실험의 LCP·오류율 지표를 정의한다.
4. 인프라 팀과 자사 ROA 상태, RPKI invalid 처리 정책, 외부 의존성 장애 전환 시간을 확인한다.
5. 에이전트 하네스 설정을 코드처럼 버전 관리하고 권한 확대 없는 sandbox 평가를 만든다.
